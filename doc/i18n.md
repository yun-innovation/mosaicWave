# i18n and l10n

Milestone 3 (done). The web UI and user-facing server errors can be shown in English, Traditional Chinese, and Simplified Chinese. Agent rule: [`.cursor/rules/i18n.mdc`](../.cursor/rules/i18n.mdc).

## Locales

| Locale | Language | Browser tags that select it |
| --- | --- | --- |
| `en` | English (default, source text) | everything not listed below |
| `zh-Hant` | Traditional Chinese | `zh-HK`, `zh-TW`, `zh-MO`, `zh-Hant*` |
| `zh-Hans` | Simplified Chinese | `zh-CN`, `zh-SG`, `zh`, `zh-Hans*` |

A missing key falls back to `en`.

## Web UI

- Library: `i18next` + `react-i18next`. Resources are bundled into the static export (imported JSON, no HTTP backend), because the UI is a single static page served by FastAPI.
- Files: `src/web/app/locales/{locale}/{namespace}.json`. Namespaces follow screens: `common`, `auth`, `gallery`, `import`, `settings`, `backup`, `errors`.
- Keys: `namespace:area.item` in camelCase (e.g. `settings:saveFolder.button`). English JSON is the source of truth.
- Interpolation `{{name}}`; counts as `{{count, number}}`. Plurals use i18next suffixes, which follow `Intl.PluralRules`: English needs `_one` and `_other`, Chinese only `_other`. Never end a non-plural key in `_one` / `_other`.
- Type safety: TypeScript `CustomTypeOptions` (`app/i18next.d.ts`) is typed from the English resources, so a wrong key fails `next build`.
- Completeness: `npm run i18n-check` (also the `prebuild` step) fails when `zh-Hant` or `zh-Hans` has a missing, extra, or empty key, or different `{{placeholders}}`, compared to `en`. It also scans `src/server/mosaicwave` for error and warning codes and fails if one has no `errors:{code}` in English.
- Formatting: `app/format.ts` (`formatDate`, `formatDateTime`, `formatDay`, `formatMonth`, `formatNumber`, `formatBytes`) uses `Intl` with the active locale. Do not pass `undefined` as the locale.
- Code in `useCallback` / `useEffect` uses `i18n.t`, not the hook's `t`, so a language switch does not reload Settings or reset the folder picker.
- `document.documentElement.lang` follows the active locale (the static export renders `lang="en"` and switches after hydration).

## Choosing the locale

1. Signed-in user's saved choice (`user.locale`).
2. Last choice in this browser (`localStorage` key `mosaicWave.locale`), for the sign-in screen before anyone is signed in.
3. `navigator.languages`, mapped with the table above.
4. `en`.

Settings has a language menu: Automatic (follow the browser), English, 繁體中文, 简体中文. Changing it switches the UI at once, saves to the server, and updates `localStorage` (Automatic clears it). The menu shows the account's choice, else this browser's. The sign-in screen has no menu; it follows steps 2–4.

## Server

- `user.locale` VARCHAR(16) NULL — a locale from the table above, or NULL for automatic ([schema.md](schema.md)). Older databases get the column at startup.
- `GET /api/v1/me` and `GET /api/v1/auth/status` return `locale`. `PATCH /api/v1/me` with `{"locale": "zh-Hant" | "zh-Hans" | "en" | null}` sets it; anything else is 400 `invalid_locale` ([architecture.md](architecture.md)).
- Errors the UI may show carry a stable `code` and optional `params` next to the English `detail`:

```json
{ "detail": "password must be at least 8 characters", "code": "password_too_short", "params": { "min": 8 } }
```

  Raise `ApiError(status, code, detail, params)` from `mosaicwave/api/errors.py`. The UI translates `errors:{code}` with `params` and falls back to `detail`. `detail` stays, so `/api/v1` remains compatible. Codes are `snake_case`.
- When the English text comes from deeper code (a path check, an SMB mount, a zip error), `wrapped(status, code, exc)` uses a category code and passes the text as `params.message`, which the translation includes as is.
- Takeout warnings (`DumpWarning`) carry `code` and `params`; both are stored on the job and returned by the API, and use the same `errors:{code}` lookup.

## API language (milestone 8, planned)

Two different inputs. Keep them apart in code, docs, and tests:

| Input | Where | Meaning | Unsupported value |
| --- | --- | --- | --- |
| **Response language** | Every request (header or query; picked in the milestone 8 design) | Language of the text and formatted dates in this one response | Fall back: `user.locale`, then `en`. Never an error |
| **Target language** | `locale` in the body of `PATCH /api/v1/me` | The choice to save as `user.locale` | 400 `invalid_locale`; nothing saved |

- **Neither sets the other.** A response language is never saved. A target language is never guessed from the response language or `Accept-Language`. Only `PATCH /api/v1/me` changes `user.locale`.
- **Codes may differ from the UI's.** The API may accept wider BCP 47 tags (`zh-TW`, `zh-CN`, `en-GB`) for either input. The server maps them to a supported locale with the same table as the web ([Locales](#locales)) and stores and returns only the canonical code (`en`, `zh-Hant`, `zh-Hans`). The web keeps sending canonical codes.
- **Supported lists.** The server's list of target locales is authoritative. If the UI ships a locale the server does not accept yet (or the reverse), the UI must not offer it as a saved choice; the server publishes its list (for example on `auth/status`) so the menu can check.
- **Switching.** `PATCH /api/v1/me` answers in the **new** target language (for Automatic, `null`, in the request's response language), and returns the canonical `locale` it saved. The web applies the new language before its next request, so the very next response matches the UI without a reload. A request still in flight from before the switch may come back in the old language; the UI re-renders codes in the current language rather than trusting old text.
- **Caching.** Responses that vary by language carry `Vary` for the language input, so a cache never serves one language's text to another.
- **Tests** cover: a switch sent with a response language different from the target; tag normalization (`zh-TW` saved as `zh-Hant`); an unsupported target (400, nothing saved) next to an unsupported response language (falls back, 200); and the request after a switch arriving in the new language.

## Not translated

- User data: album names, filenames, folder paths, Takeout album titles
- Server logs, `mosaicWave.log`, command-line output (`wipe`, `port-who`, `mosaicWave.sh`)
- OpenAPI docs and JSON field names
- Installers (MSI wizard, QPKG App Center text, `install.sh`) — later item
- Right-to-left layout

## Done when (milestone 3)

- Every user-facing string in `src/web/app` goes through `t()`
- `zh-Hant` and `zh-Hans` are complete and `i18n-check` passes
- `user.locale` is saved and follows the user across devices
- Auth, Takeout, and Settings errors show in the chosen language
