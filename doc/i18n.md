# i18n and l10n

Milestone 3 (done). The web UI and user-facing server errors can be shown in English, Traditional Chinese, and Simplified Chinese. Agent rule: [`.cursor/rules/i18n.mdc`](../.cursor/rules/i18n.mdc).

## Locales

| Locale | Language | Browser tags that select it |
| --- | --- | --- |
| `en` | English (default, source text) | everything not listed below |
| `zh-Hant` | Traditional Chinese | `zh-HK`, `zh-TW`, `zh-MO`, `zh-Hant*` |
| `zh-Hans` | Simplified Chinese | `zh-CN`, `zh-SG`, `zh`, `zh-Hans*` |

A missing key falls back to `en`.

## Web UI

- Library: `i18next` + `react-i18next`. Resources are bundled into the static export (imported JSON, no HTTP backend), because the UI is a single static page served by FastAPI.
- Files: `src/web/app/locales/{locale}/{namespace}.json`. Namespaces follow screens: `common`, `auth`, `gallery`, `import`, `settings`, `backup`, `jobbar`, `maintenance`, `errors`.
- Keys: `namespace:area.item` in camelCase (e.g. `settings:saveFolder.button`). English JSON is the source of truth.
- Interpolation `{{name}}`; counts as `{{count, number}}`. Plurals use i18next suffixes, which follow `Intl.PluralRules`: English needs `_one` and `_other`, Chinese only `_other`. Never end a non-plural key in `_one` / `_other`.
- Type safety: TypeScript `CustomTypeOptions` (`app/i18next.d.ts`) is typed from the English resources, so a wrong key fails `next build`.
- Completeness: `npm run i18n-check` (also the `prebuild` step) fails when `zh-Hant` or `zh-Hans` has a missing, extra, or empty key, or different `{{placeholders}}`, compared to `en`. It also scans `src/server/mosaicwave` for error and warning codes and fails if one has no `errors:{code}` in English.
- Formatting: `app/format.ts` (`formatDate`, `formatDateTime`, `formatDay`, `formatMonth`, `formatNumber`, `formatBytes`) uses `Intl` with the active locale. Do not pass `undefined` as the locale.
- Code in `useCallback` / `useEffect` uses `i18n.t`, not the hook's `t`, so a language switch does not reload Settings or reset the folder picker.
- `document.documentElement.lang` follows the active locale (the static export renders `lang="en"` and switches after hydration).

## Choosing the locale

1. Signed-in user's saved choice (`user.locale`).
2. Last choice in this browser (`localStorage` key `mosaicWave.locale`), for the sign-in screen before anyone is signed in.
3. `navigator.languages`, mapped with the table above.
4. `en`.

Settings has a language menu: Automatic (follow the browser), English, 繁體中文, 简体中文. Changing it switches the UI at once, saves to the server, and updates `localStorage` (Automatic clears it). The menu shows the account's choice, else this browser's. The sign-in screen has no menu; it follows steps 2–4.

## Server

- `user.locale` VARCHAR(16) NULL — a locale from the table above, or NULL for automatic ([schema.md](schema.md)). Older databases get the column at startup.
- `GET /api/v1/me` and `GET /api/v1/auth/status` return `locale`. `PATCH /api/v1/me` with `{"locale": "zh-Hant" | "zh-Hans" | "en" | null}` sets it; anything else is 400 `invalid_locale` ([architecture.md](architecture.md)).
- Errors the UI may show carry a stable `code` and optional `params` next to the English `detail`:

```json
{ "detail": "password must be at least 8 characters", "code": "password_too_short", "params": { "min": 8 } }
```

  Raise `ApiError(status, code, detail, params)` from `mosaicwave/api/errors.py`. The UI translates `errors:{code}` with `params` and falls back to `detail`. `detail` stays, so `/api/v1` remains compatible. Codes are `snake_case`.
- When the English text comes from deeper code (a path check, an SMB mount, a zip error), `wrapped(status, code, exc)` uses a category code and passes the text as `params.message`, which the translation includes as is.
- Takeout warnings (`DumpWarning`) carry `code` and `params`; both are stored on the job and returned by the API, and use the same `errors:{code}` lookup.

### Still in English

Locale date/time in API responses is the rest of milestone 8 (see [API language](#api-language-milestone-8)). Until then:

## API language (milestone 8)

Status: the response language for error text (`detail`, PR 1), for job text and warnings (PR 2), and the display time zone (PR 3) are done.

Two different inputs. Keep them apart in code, docs, and tests:

| Input | Where | Meaning | Unsupported value |
| --- | --- | --- | --- |
| **Response language** | The header `X-MosaicWave-Language: zh-Hant` or the query `?lang=zh-Hant` on any request (the header wins when both are given) | Language of the text and formatted dates in this one response | Fall back: `user.locale`, then `en`. Never an error |
| **Target language** | `locale` in the body of `PATCH /api/v1/me` | The choice to save as `user.locale` | 400 `invalid_locale`; nothing saved |

- **Neither sets the other.** A response language is never saved. A target language is never guessed from the response language or `Accept-Language`. Only `PATCH /api/v1/me` changes `user.locale`.
- **Codes may differ from the UI's.** The API may accept wider BCP 47 tags (`zh-TW`, `zh-CN`, `en-GB`) for either input. The server maps them to a supported locale with the same table as the web ([Locales](#locales)) and stores and returns only the canonical code (`en`, `zh-Hant`, `zh-Hans`). The web keeps sending canonical codes.
- **Supported lists.** The server's list of target locales is authoritative. If the UI ships a locale the server does not accept yet (or the reverse), the UI must not offer it as a saved choice; the server publishes its list (for example on `auth/status`) so the menu can check.
- **Switching.** `PATCH /api/v1/me` answers in the **new** target language (for Automatic, `null`, in the request's response language), and returns the canonical `locale` it saved. The web applies the new language before its next request, so the very next response matches the UI without a reload. A request still in flight from before the switch may come back in the old language; the UI re-renders codes in the current language rather than trusting old text.
- **Caching.** Responses that vary by language carry `Vary` for the language input, so a cache never serves one language's text to another.
- **`Accept-Language` is not read at all.** A browser sends it on its own, so honoring it would change answers behind the user's back; only the header or query above names a language.
- **How `detail` is written.** `code` and `params` never change. With `en` (or nothing named and no saved locale), `detail` is the server's own English sentence. With another language the server renders `errors:{code}` from its own catalog with `params` (`{{name}}` placeholders; a plural entry uses `_one` when `count` is 1, else `_other`) and falls back to the English `detail` when the code has no entry. Only `/api/v1` JSON answers carry `Content-Language` (the language written) and `Vary: X-MosaicWave-Language, Cookie`.
- **Server catalog.** `src/web/app/locales/<locale>/errors.json` stays the only place the texts are written. `npm run sync-locales` copies them to `src/server/mosaicwave/locales/errors.<locale>.json` (committed, packaged with the server); `npm run i18n-check` (also the `prebuild` step, so CI) fails when a copy is stale or missing. After changing `errors.json`, run `npm run sync-locales` and commit the result.
- **Web.** Every request from the web carries `X-MosaicWave-Language` with the page's current language. `auth/status` returns `locales` (the languages the server answers and saves in); the Settings language menu offers only those the web also ships.
- **Job text** (PR 2). Every line a job writes for a person (`job.error`, `job.current`, each `job_event.message`) is a code from `jobtext.py` (`jt("job_import_done", assets=3, albums=1)`) with params, stored next to the English sentence (`error_code`/`error_params`, `current_code`/`current_params`, `job_event.code`/`params`; schema step 4). The English text stays in the old fields, so older clients and logs read plain English; `GET /jobs/{id}`, `/jobs/{id}/events` and the other job views render the code in the response language when read, so a job written under one language reads in another. A text with no code is data and is never translated: a photo path in `current`, and an exception's own message, which `job_failed` / `job_failed_at` carry as `params.message`. Job codes (`job_*`) live in `errors.json` with the rest.
- **Warnings** (PR 2). A Takeout warning's `message` is rendered from its `code` + `params` (`no_takeout_zips` gets its second sentence, as in the web). Backup and export warnings are English sentences in the archive manifests (kept, so old archives and clients still read them); the API recognises the known ones (`job_warn_*` templates) and returns them in the response language, and leaves any other sentence as written.
- **Time zone** (PR 3). Everything stored and every timestamp field the API sends (`created_at`, `updated_at`, `taken_at`, `rev` ordering and the like) is UTC, ISO 8601, whatever a user picks. The user chooses the zone times are *shown* in: `user.time_zone`, an IANA name (`Asia/Taipei`) or `null` for the default, **UTC** (not the server's or the device's zone, so every device shows the same times until its user picks a zone), saved with `PATCH /api/v1/me` (`{"time_zone": "Asia/Taipei"}`) and returned in `me.time_zone`. The zone data comes from the `tzdata` package only, never from the operating system (`mosaicwave/timezone.py` points `zoneinfo` at an empty search path): Windows has no zone files and a NAS may have none or old ones, so the OS would give a different list and different rules on each platform; with `tzdata` they are the same everywhere and change only when the package is upgraded. `GET /api/v1/time-zones` returns that list (`{version, zones}`: `UTC` first, then every real place under an IANA area such as `Asia/` or `Europe/`, A to Z; legacy aliases like `US/Pacific` are left out but still accepted), and the web picker is built from exactly those and shows `UTC` while no zone is saved, so the web and the server never disagree about a name (the browser's own list is used only against an older server that has no such call). The server checks the name against that database, stores the database's spelling (`asia/taipei` becomes `Asia/Taipei`), and answers `400 invalid_time_zone` for anything else (or `503 time_zone_data_missing` when the server has no zone database at all, for example a development virtual environment made before `tzdata` was added: run `pip install -e ".[dev]"` again), saving nothing, not even a `locale` sent in the same body. `locale`, `time_zone` and `use_dst` are separate: a body that names one leaves the others alone. **Summer time**: `user.use_dst` (boolean, default `false`, `PATCH /me` `{"use_dst": true}`; `null` is ignored) says whether a zone that has summer time follows it. Off, times are held at the zone's standard offset all year (the smaller of its January and July offsets), so the app's clock never jumps because of where a user or the server happens to be; on, the zone's own rules apply. The server only stores the switch; the web applies it in `format.ts` (a fixed offset such as `+01:00` as the `Intl` zone) and offers the checkbox only when the chosen zone observes summer time (its January and July offsets differ). The web shows times with `Intl.DateTimeFormat({ timeZone })` in `format.ts` (day grouping in the timeline uses the zone too, so a photo taken near midnight UTC lands on the user's own day) and offers the choice in Settings only (not in the account menu), next to the language. **Every producer is UTC** (checked by `tests/test_utc_contract.py`, which on Linux moves the host to Pacific/Auckland first so any use of local time shows up): every time field the API sends is ISO 8601 UTC with an offset (`...Z`; naive values that SQLite returns are read as UTC and written with the `Z` by `iso_utc` in `models.py`); Takeout import reads `photoTakenTime.timestamp` as an epoch, file times as UTC epoch seconds; backups and restores copy database values untouched and write and read zip entries through `ziptime.py` (the plain zip time is the UTC wall clock and the Info-ZIP extended-timestamp field holds the exact second); exports use the same helper for every entry (both zip layouts) and write Takeout sidecars with an epoch `timestamp` and a `formatted` string ending in `UTC`, so an exported Takeout imports back to the same instant. **Known limit:** an EXIF `DateTimeOriginal` carries no zone, so it is read as if it were UTC (the camera's wall clock shown as it was taken); a photo from a camera in another zone can therefore sort a few hours away from a photo that has a true instant (a Takeout sidecar). Any date the API itself writes inside a sentence must use the user's zone and the response language; none does today (job lines carry no times, and file names, zip entries and Takeout `photoTakenTime` stay UTC by design).
- **Tests** cover: a switch sent with a response language different from the target; tag normalization (`zh-TW` saved as `zh-Hant`); an unsupported target (400, nothing saved) next to an unsupported response language (falls back, 200); and the request after a switch arriving in the new language.

## Not translated

- User data: album names, filenames, folder paths, Takeout album titles
- Server logs, `mosaicWave.log`, command-line output (`wipe`, `port-who`, `mosaicWave.sh`)
- OpenAPI docs and JSON field names
- Installers (MSI wizard, QPKG App Center text, `install.sh`) — later item
- Right-to-left layout

## Done when (milestone 3)

- Every user-facing string in `src/web/app` goes through `t()`
- `zh-Hant` and `zh-Hans` are complete and `i18n-check` passes
- `user.locale` is saved and follows the user across devices
- Auth, Takeout, and Settings errors show in the chosen language
