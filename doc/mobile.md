## What the apps need from this repo

Everything the web does already works over plain HTTPS JSON. The gaps, each its own PR here, in this order:

1. **Published contract (done).** `openapi/openapi.json` is generated by `python -m mosaicwave.openapi_export` and committed; `tests/test_openapi_file.py` fails CI when it is stale, so the app repo can pin a commit of it. Postman is kept current as before. Compatibility rule: additive changes only inside `v1` (a removed or renamed field or parameter means `v2` or a compatibility window, [process.md](process.md)).
2. **App sign-in (done).** The session is a signed value (cookie `mw_session`, `auth/session.py`). An app sends the same value as `Authorization: Bearer <value>`: `POST /auth/login` with `{"token": true}` returns it in the body (`session_token`, `expires_in`) and sets no cookie, and `POST /auth/refresh` returns a fresh one. No second token system; the web is unchanged. An app session lasts 90 days by default (the browser 14); both are admin settings. A session is a stored row an admin-set lifetime applies to (90 days for apps by default), listed and revocable per device (`/me/sessions`, Settings → Signed-in devices). Details: [architecture.md § App sign-in](architecture.md#app-sign-in-bearer-header).
3. **Server discovery (done).** `GET /auth/status` answers without a session with `platform`, `needs_setup`, `locales` and now `server_version`, `api_version` (`v1`) and `min_app_version` (`MIN_APP_VERSION` in `mosaicwave/__init__.py`, raised only with a breaking `/api/v1` change). An app older than `min_app_version` asks its user to update instead of failing in odd ways. The app compares dotted numbers (`0.1.0`).
4. **Resumable upload.** The client-upload session (`/import/takeout/push` family) is for a Takeout dump and runs the Takeout ingest at the end. A phone uploads single photos over a bad network, so it needs a normal upload endpoint: create an upload (`name`, `size`, `taken_at`, a client content hash), `PUT` chunks with offsets, `HEAD` to learn how much arrived, and a finish that runs the usual import for one file. Duplicates are answered by hash before any bytes are sent (the server already dedupes on content). Written as its own design section in this page before code.
5. **Lighter list calls** (only if the app needs them after real use): smaller thumbnails sizes, a changes-since call for the replica (`rev` and `deleted_at` already exist on every table), and ETag on thumbnails.

Not needed from this repo: push notifications, share links (milestone 11), a mobile-only API.

## The app, in outline

- **Sign in:** server URL, then username and password through `POST /auth/login` (the server checks them with the QNAP or local provider). The URL and session value live in the platform's secure storage. The app sends its language in `X-MosaicWave-Language` and shows dates in the account's `time_zone` and `use_dst`, the same rules as the web ([i18n.md](i18n.md)): the server stores and sends UTC, the client formats.
- **Browse:** the timeline is `GET /assets` with cursor paging, `GET /assets/months` for the scrubber, search through `q`, `taken_from` and `taken_to`; albums through `/albums`. Thumbnails are cached on disk by asset id.
- **Select many, export:** the same album and export endpoints as the web.
- **Offline replica:** metadata only, per [schema.md](schema.md#client-replica-web--mobile); pushes carry `base_rev`; a `409` means refetch and ask. Last in the order.

## Upload and the operating system

Uploading while the app is closed is limited by each OS, not by this repo. Android can run a long task through its work manager; iOS only gives short background windows and a system-managed background transfer. So the upload endpoint must be **resumable and idempotent** (a killed transfer picks up at the byte it reached; sending a photo twice never makes two). What the app does on each OS belongs in the app repo's own notes.

## Upload design (step G)

**Status: server side built** (`/api/v1/uploads`, merged in #63); the app's uploader is not. The open points were settled on 2026-11-10 (the `removed` rule; no device album, files go to `Uploads/{year}`). It replaces nothing: the Takeout push session (`/import/takeout/push`) stays for dumps.

### Why a new endpoint

The Takeout push is one job per dump that ends in a Takeout ingest (sidecars, album folders). A phone sends single photos and videos, over networks that drop, from an OS that may kill the app. It needs: skip what the server already has, resume at the byte reached, verify the bytes, and finish one file into the library, all without a job per photo.

### The protocol (tus-shaped, not tus)

The verbs and headers follow [tus 1.0](https://tus.io/protocols/resumable-upload) (`Upload-Offset`, `Upload-Length`, `HEAD` to resume, `PATCH` to append) so a client can use a tus library or write the few calls by hand. It is **not claimed to be tus-compliant**: bodies are JSON, errors are the usual `{detail, code, params}`, and auth is the usual bearer header. All paths are under `/api/v1`, all need a session, all act only on the caller's own uploads.

| Call | What it does |
| --- | --- |
| `POST /uploads/check` | `{items: [{content_hash, size}]}` (at most 500) answers `{known: [hash…], removed: [hash…]}`: hashes the library already has, and hashes of photos the user deleted on purpose. The app skips both; one request replaces hundreds of attempts. |
| `POST /uploads` | `{filename, size, content_hash, taken_at?, mime?}` starts an upload and answers `201 {id, offset: 0, chunk_size, expires_at}`. **Idempotent** per `(user, content_hash)`: if one is already open it answers `200` with the same `id` and the offset it has reached, so an app that lost its state resumes without a list call. If the library already has the hash: `200 {state: "exists", asset_id}` and nothing is uploaded. |
| `HEAD /uploads/{id}` | Headers `Upload-Offset` and `Upload-Length`: where to continue. `404` once finished, aborted or expired. |
| `PATCH /uploads/{id}` | Raw bytes (`Content-Type: application/offset+octet-stream`) with `Upload-Offset: <n>`. Appends when `n` equals the server's offset, else `409 upload_offset_mismatch` with the true `offset` in `params`. Answers the new offset. A small file is `POST` + one `PATCH`. |
| `DELETE /uploads/{id}` | Abort and delete the partial file. |

The last byte completes the upload **in the same response**: the server checks the SHA-256 of the whole file against `content_hash` and answers `{state: "done", asset: {…}}` (the usual asset JSON). A mismatch deletes the partial file and answers `422 upload_hash_mismatch`; the app starts that photo over. A `PATCH` that would pass `Upload-Length` is refused (`400 upload_too_long`) and changes nothing.

`content_hash` is the SHA-256 in lower-case hex, the same value the server stores in `asset.content_hash` for Takeout imports, so a photo imported from Takeout earlier is recognised and not uploaded again. An asset found by a folder scan may have **no stored hash**; the server does not read every file to find out, so such a photo is not recognised by `check`, `POST /uploads` or the finish step and the same photo can then be added a second time under `Uploads/{year}/`. Takeout imports and uploads always store the hash, and so does deleting a photo.

### On the server

- **Staging:** `{data_dir}/tmp/uploads/{user_id}/{id}.part` with a small `{id}.json` beside it (filename, size, hash, `taken_at`, created, last touched). No database table, so no schema step. Open uploads survive a restart; those untouched for 7 days are deleted at start-up and whenever a new upload starts.
- **Finishing a file:** the same steps as one Takeout file, minus sidecars: read the capture time (EXIF, then video metadata, then the app's `taken_at`, then the file time), pick a free name (`unused_relative`), move the file into the user's library folder, add the asset with its hash, queue the thumbnail. Stored under `Uploads/{year}/{filename}` so it is easy to find in the folder tree and by name search; the year is the capture year in UTC.
- **Which device it came from (decided: not tracked):** the server does not record or sort by the uploading device. Photo management does not need it: a file keeps whatever its own EXIF says about the camera, everything lands in `Uploads/{year}`, and the library works the same for photos from any device. Only the session list ("Signed-in devices") knows device names.
- **Limits (settings, not constants in the app):** a file at most 64 GiB; at most 100 open uploads per user; free space on the data folder is checked when an upload starts (`507 insufficient_storage`); only photo and video types the library already accepts (`415 unsupported_media_type`, judged by file name, then confirmed when the metadata is read).
- **Safety:** `filename` is reduced to a plain name (no folders, no reserved names); a second `PATCH` to the same upload while one runs is refused (`409 upload_busy`); another user's upload id is `404`; maintenance mode blocks uploads like every other write.
- **Time:** all times are UTC ISO 8601 with `Z`, as everywhere ([i18n.md](i18n.md)).
- **Errors** get codes in all three languages, like the other API errors (`upload_offset_mismatch`, `upload_hash_mismatch`, `upload_too_long`, `upload_busy`, `unsupported_media_type`, `insufficient_storage`).

### How an app learns a photo was removed

The rule is about the **file**, not the device: `removed` is answered by `content_hash`, so it works the same whether or not the device can be traced (the server does not track the uploading device at all, so there is nothing to trace). Three things make it hold:

1. **The server keeps a tombstone.** Removing a photo soft-deletes its row (`deleted_at`), and the row keeps its `content_hash`; `check` reports that hash as `removed`. Two gaps to close in the endpoint PR or just before it: (a) **there is no "delete a photo" call today** (only albums and sources can be deleted; a photo is marked deleted only when a rescan finds its file gone), so the PR adds `DELETE /assets/{id}` for the web and apps, soft-deleting and never dropping the hash; (b) assets found by a folder scan may have **no stored hash**, so the delete computes it (reads the file once) before the row is marked deleted. A photo whose file was deleted outside the app has no bytes left to hash; it is only `removed` if it had a hash already.
2. **Another device sends the same file.** The same hash is `removed` for every device of the same user, so a phone and a tablet holding the same photo both skip it.
3. **The app keeps its own ledger** of hashes it has uploaded or been told are `known` or `removed`, so it never depends on the server alone and does not re-hash or re-ask for each photo on every run. A new install starts with an empty ledger and one `check` rebuilds it.

What this cannot do: a *different file* of the same scene (re-saved, edited, re-compressed) has a different hash and is uploaded as new. That is intended.

### What the app does (for its own notes)

- Hash on the phone (streaming, not into memory), call `check` for a batch, create and send the rest in chunks of 8 MiB (the server's `chunk_size` is a hint; any size up to 64 MiB works). The chunk size is small enough for iOS background transfers and Android work-manager tasks to make progress and be retried.
- After a failure: `HEAD`, continue at `Upload-Offset`. After losing all state: `POST /uploads` again with the same hash gets the same upload back.
- A photo the user deleted on the server is in `removed` and is not uploaded again (**decided**; to be refined once the Flutter client is working). Whether the app offers "upload anyway" is the app's choice; the server accepts a fresh upload of a removed hash, and finishing it restores nothing: it is a new asset.
